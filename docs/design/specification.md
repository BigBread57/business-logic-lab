# Business Logic Lab — спецификация первого выпуска

Статус: подтверждена пользователем, реализация начата. Дата: 2026-10-22. Первый проект: speech-analytics и raw-data-consumer, включая межсервисную цепочку через OpenSearch. Это подтверждение продукта не заменяет согласование конкретных правил RSA.

## Результат

Навык для Codex с переносимыми инструкциями, шаблонами и вспомогательными скриптами. Пользователь задаёт проект, бизнес-процесс, среду, полномочия и бюджет; агент исследует поведение с разных сторон, пишет отчёт и создаёт регрессионные тесты. Перенос на другие хосты — последующий этап, совместимость пока не заявляется.

Первая приёмка — на реальном проекте пользователя, без разработки отдельного демонстрационного приложения. Выбраны speech-analytics, raw-data-consumer и OpenSearch. По исследованию исходников фактическая цепочка включает PostgreSQL, analytics worker, RSA Kafka и Data Prepper; прямого бизнес-REST API у RAW нет. Для первого запуска предложен процесс одного синтетического завершённого чата с проверкой downstream-идентичности, дублей и поздних обновлений; бизнес-правила и среда запуска требуют отдельного согласования.

## Подготовка знаний

Агент читает выбранные репозитории, предоставленную документацию, API-контракты и описание бизнес-процесса. Готовит пакет знаний: сущности, роли и владение объектами, состояния и переходы, операции, инварианты, побочные эффекты, временные ожидания, источники и нерешённые вопросы.

Каждое правило получает идентификатор, источник и статус. Пользователь согласовывает эталон; запуск ссылается на конкретную согласованную версию. Предположение, полученное из кода, не считается независимым подтверждением правильности кода. Подготовка и согласование знаний — отдельный этап перед бюджетом тестового запуска. Изменившийся источник отмечается для пересогласования затронутых правил.

## Конфигурация проекта и запуска

Перед каждым запуском агент составляет план тестирования из исходной задачи. Он выбирает функционал, бизнес-процессы, нужные роли приложения, число аккаунтов и исполнителей. Эти числа независимы: несколько исполнителей могут иметь одну роль с разными аккаунтами; один исполнитель при необходимости работает с несколькими ролями. Настройки разрешаются и показываются до старта тестового бюджета, с учётом уже заданных пользователем полномочий. Уточняются только недостающие решения, необходимые для запуска; повторного согласования уже разрешённых действий не требуется.

- Репозитории, источники знаний и выбранный бизнес-процесс.
- Локальная Docker-среда либо dev; разрешённые адреса и ресурсы стенда.
- Аккаунты, роли, способ получения секретов; секреты не включаются в отчёты и тестовые исходники.
- Разрешённые изменения, создание аккаунтов/данных, сброс, нагрузка и сбои.
- Для выделенного локального стенда пользователь разрешил полный доступ; для dev действует настраиваемый ограниченный профиль.
- Профиль нагрузки: интенсивность, параллелизм, продолжительность и условия остановки. Значения задаются для конкретного проекта.
- Структура команды, бюджет времени и место сохранения результатов.
- Общий бюджет запуска по умолчанию — 20 минут, включая техническую подготовку сессий, эксперименты, генерацию/проверку тестов и отчёт. Он не включает предшествующее согласование знаний.

План фиксирует назначения «исполнитель → ракурс проверки → роль приложения → аккаунт/сессия → функционал», сценарии и ожидаемые результаты либо открытые вопросы. Для конкурентных действий назначаются общий объект, начальное состояние, точка синхронизации и проверка общего результата. Для нагрузки назначаются ответственные исполнители, инструменты, распределение ролей, интенсивность/число повторов, параллелизм, длительность, общие лимиты и условия остановки. Каноническая инструкция и шаблон: [подготовка запуска](../../.agents/skills/business-logic-qa/references/planning.md).

Инструкции и проверки параметров не равны системной изоляции. Политики встроенных скриптов проверяются в скриптах; произвольные действия агента ограничиваются доступными средствами хоста. Продукт не обещает принудительную изоляцию без соответствующего механизма.

## Выполнение

По умолчанию координатор распределяет задания исполнителям; состав команды настраивается. Ракурсы: полные процессы и переходы; роли/владение; повторы/порядок действий/конкуренция; нагрузка и бизнес-результаты. Число ракурсов не требует такого же числа одновременно работающих агентов.

UI и API — обязательные возможности навыка, чтение кода — источник гипотез. БД и события используются при наличии доступа. Отсутствующий канал фиксируется как ограничение, а не успешно пройденная проверка. Сам QA-запуск не исправляет код приложения.

Аккаунты имеют независимые сессии. Независимые эксперименты используют выделенные данные; общий объект назначается явно для проверки конкуренции. Отдельные подагенты не гарантируют отдельные браузерные сессии — изоляцию обеспечивает исполнитель.

Агент проверяет не только описанный корректный путь. Для выбранного функционала он обязан сформировать релевантные пограничные и негативные сценарии: значения на границе и за ней, пропущенные/неверные поля, намеренное нарушение порядка и контрактов, запрещённые действия, повторы, устаревшие состояния, конфликтующие одновременные операции и действия в обход ограничений UI через разрешённое API. Применимые сбои/частичное выполнение проверяются в рамках профиля среды. Пропущенные классы сценариев и причины фиксируются в покрытии.

Ожидание отрицательного сценария берётся из согласованного правила или контракта: отказ, допустимая нормализация и сохраняемые инварианты. Необычный принятый запрос сам по себе не дефект. При неизвестном ожидаемом результате агент фиксирует пробел, наблюдения и независимо проверяемые инварианты. Проверяются частичные записи и побочные эффекты, а не только код ответа.

Для каждого сценария сохраняются правило, начальное состояние, участники, действия, ожидаемый и фактический результат, временные метки и доказательства. Различаются нарушение эталона, пробел процесса, противоречие документации/кода, гипотеза и ограничение среды. Серьёзность и уверенность указываются отдельно.

При новом пробеле агент записывает его и продолжает независимые проверки; зависимый результат остаётся неопределённым. Для асинхронных процессов учитываются согласованные окна сходимости. HTTP-коды сами по себе не доказывают корректность бизнес-результата.

## Контекст и длительные запуски

Исполнители получают небольшие задания и относящиеся к ним правила. Промежуточные результаты, очередь сценариев, выполненные проверки, ограничения и доказательства сохраняются инкрементально. У каждого исполнителя отдельные файлы, общий индекс обновляет координатор.

Координатор получает краткие сводки и ссылки на артефакты. После прерывания продолжение восстанавливается по сохранённому состоянию и исходному дедлайну; новое продление бюджета не предполагается автоматически. Нельзя повторять неизвестно завершившуюся мутацию без сверки её результата.

При приближении дедлайна прекращается выдача новых экспериментов и резервируется время на фиксацию результатов. Незавершённые задачи отражаются в отчёте. Точные ограничения таймаута зависят от доступных механизмов исполнения; один промпт не гарантирует остановку уже отправленной серверной операции.

## Отчёты и регрессионные тесты

Обязательны Markdown-отчёт и JSON, матрица проверенных правил, доказательства, replay-сценарии и автоматически созданные регрессионные тесты для подтверждённых дефектов.

Тест закрепляет ожидаемое бизнес-поведение и падает при сохраняющемся дефекте. Его нельзя ослаблять, менять эталон или помечать пропуском ради зелёного результата. До исправления такой тест может блокировать CI: отчёт должен явно показывать этот статус. Изменение пайплайна и публикация в целевой репозиторий не считаются автоматически выполненными.

Для пробелов и неоднозначностей тест не придумывает ожидаемый результат. Для нестабильной гонки тест помечается как вероятностный, если точное расписание недоступно; один seed не объявляется гарантией воспроизведения.

Тесты следуют существующему стеку целевого репозитория, создают/получают нужные данные без захардкоженных секретов и имеют команду запуска. Если время или доступ не позволяют генерацию/проверку, сохраняется явная незавершённая задача. Сгенерированный, но не выполненный тест не объявляется проверенным.

## Проверка готовности

На выбранном реальном процессе нужно продемонстрировать: подготовку согласуемых правил; минимум один сценарий полного процесса; проверки нескольких аккаунтов/ролей, если они применимы; UI/API-наблюдения; запись покрытия и пробелов; соблюдение заданного профиля среды; сохранение/восстановление состояния; отчёты и replay.

Если найден подтверждённый дефект, создаётся и запускается регрессионный тест, проверяется соответствие его результата находке. Если дефектов не найдено, способность преобразования подтверждённой находки в тест остаётся отдельно непроверенной; нельзя объявлять её подтверждённой лишь по отсутствию ошибок. Для её проверки можно использовать ранее известный воспроизводимый дефект реального проекта.

Приёмка не требует заранее заданного числа найденных багов и не доказывает полную корректность системы.

## Осталось подтвердить

Общее понимание спецификации подтверждено; проекты выбраны. Остаются согласование конкретных RSA-правил и среды, затем живая приёмка. Реализация и независимая проверка инструмента продолжаются без ожидания этих предпосылок.

## Дополнение: генерация и исследовательские истории

Навык формирует разнообразные валидные синтетические данные из структурных контрактов и согласованных бизнес-условий; сохраняет seed, конкретные значения, IDs и предпосылки. Каждая выбранная функция проверяется неоднократно с вариациями вводов, числа/порядка действий и конкурентных расписаний в пределах бюджета. Намеренно невалидные случаи маркируются отдельно. В режиме проверки эталона доступны business pass/fail; в исследовательском режиме неизвестные ожидания сохраняются для последующего разбора, а известные инварианты проверяются независимо. История intent/result/observation сохраняет роли, сессии, причинные связи и неизвестно завершившиеся действия. Структурный анализ журнала не подменяет анализ общей истории координатором. Канонические детали: [exploration](../../.agents/skills/business-logic-qa/references/exploration.md).

Новый запуск папок: speech-analytics + speech-analytics-front, два Analyst и один Users; по последнему уточнению пользователя 10 минут, общий лимит 250 операций, максимум 4 параллельных операции. Видимость общего пространства обычному Users оставлена открытым вопросом, проверяется по коду и UI/API как наблюдение, а не утверждённый отказ. Остальные согласованные правила сохранены в projects/rsa-folders/knowledge.v1.json.

## Дополнение: базовые паттерны и самостоятельный вывод проверок

Для каждой выбранной функции агент рассматривает [базовый каталог](../../.agents/skills/business-logic-qa/references/patterns.md), сохраняет применимость и конкретные сценарии в отдельной матрице. Затем исследует код, контракты, состояния, владельцев, ограничения хранилищ, транзакции и побочные эффекты для дополнительных проектных гипотез; после наблюдений обновляет их очередь. Неизвестность, отсутствие исполнителя и нехватка бюджета отражаются отдельно. Требования внешнего стандарта и знакомые примеры ошибок сами по себе не утверждают бизнес-эталон. Матрица обязательна как процесс агента, но не проверяется автоматически CLI. Подключение каталога не означает установку упомянутых внешних инструментов или реализацию файлового адаптера.
