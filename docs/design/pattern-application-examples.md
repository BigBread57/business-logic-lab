# От каталога ошибок к проверкам конкретной функции

Ниже примеры подготовки плана, а не новые результаты тестов. Канонический процесс — [patterns.md](../../.agents/skills/business-logic-qa/references/patterns.md), шаблон — [матрица](../../.agents/skills/business-logic-qa/assets/pattern-matrix.example.md).

## Загрузка файла

Базовые направления: структура входов P01, строки P02, файлы P11–P12, лимиты P15, UI P19. Агент готовит настоящие допустимые файлы и независимо меняет имя, расширение, заявленный тип, содержимое, размер и способ отправки. Отдельно проверяет последующее чтение/обработку и доступ другого тестового пользователя. Нельзя считать переименованный произвольный текст валидным PDF или считать HTTP 200 доказательством обработки.

Затем агент читает именно этот pipeline. Если он сохраняет файл, создаёт задачу и позже записывает распознанный текст, возникают дополнительные вопросы: что происходит при повторной доставке задачи, отмене во время обработки и ошибке после сохранения файла; какие связанные данные должны быть очищены; как статус UI связан с фактическим результатом. Ожидаемые эффекты нужны из требований, не из названия операции.

Если нет исполняемого генератора нужного формата или multipart-клиента, сценарий помечается blocked и требует адаптера. Библиотека подсказок сама этого пробела не закрывает. Fault-сценарии выполняются только в пределах разрешённого профиля и лимитов.

## Перенос папки

База: права P03–P05, состояние P06, конкуренция P07, иерархия P13. Два аккаунта работают с одной папкой, разными назначениями и явно зафиксированной версией; отдельно выполняются последовательные переносы и варианты без версии. Известное правило конфликта не переносится автоматически на версии, для которых его не согласовали.

Дополнения зависят от кода. Если перемещается поддерево, пересчитывается глубина или сбрасывается кэш видимости, проверяются конкретные потомки, предел глубины и затронутые представления. Если проверка родителя и запись находятся в разных границах транзакции, комбинируются перенос и удаление родителя. Это гипотезы из реализации, а не просто повтор готового сценария с новым именем папки.

## Доступ к чужому объекту

База P03–P05 раскладывается на роль × владелец/tenant × состояние × операция. Владелец А создаёт выделенный объект и успешно выполняет разрешённое действие; пользователь Б проверяет доступ к тому же известному ID через list, detail, PATCH/PUT, удаление, поиск, экспорт и bulk, если они есть. Проверяются ответы и отсутствие изменений/утечек; ситуация «не работает ни у А, ни у Б» не подтверждает корректную авторизацию.

Проектные дополнения берутся из разных реализаций маршрутов: например, список использует policy-фильтр, а detail — другой repository; bulk вызывает общий сервис иначе; кэш ключуется без роли; после публикации меняется режим доступа. Для каждого такого факта записываются source pointer, гипотеза и способ наблюдения. Публичный по эталону объект не становится уязвимостью только потому, что его читает не владелец.

## Как выглядит результат подготовки

План ссылается на отдельную матрицу по выбранным функциям. Она показывает применимые и неприменимые направления, конкретные сценарии и происхождение идей, ожидаемый результат либо пробел, приоритет, исполнение и доказательства. Деферированный по бюджету случай остаётся применимым и непроверенным. Новая неожиданность порождает связанную гипотезу и следующий ограниченный эксперимент.

Маркировка «executed» требует записи реального действия/результата; наличие строки в каталоге или файла теста этого не доказывает. Содержательную достаточность матрицы проверяет агент/ревьюер; текущий CLI её не валидирует автоматически.
