## Согласовано — раунд 1

### Q1. Форма поставки и переносимость

Варианты: пакет инструкций/навык для существующих агентов; самостоятельный CLI с подключением моделей; сервис с интерфейсом.

Рекомендация: пакет для существующих агентов с переносимыми Markdown-инструкциями и вспомогательными скриптами. Проверять переносимость на двух конкретных агентах.

Ответ пользователя: «Навык и инструкции для существующих агентов». Конкретные хосты и проверка переносимости пока не выбраны.

### Q2. Источник правильного поведения

Варианты: утверждённые правила — эталон, прочее — предположения; модель сама выбирает вероятное поведение; любое расхождение — находка без определения правоты.

Рекомендация: утверждённые бизнес-правила — эталон; противоречия и пробелы отдельно от подтверждённых дефектов. Код — источник гипотез, а не независимое доказательство корректности.

Ответ пользователя: будет эталонный бизнес-процесс, который должен работать при проверке с разных направлений. Все нестыковки, неописанные процессы и расхождения с кодом фиксируются. Формат классификации находок ещё уточняется.

### Q3. Среда и допустимые воздействия

Варианты: выделенный тестовый стенд с ограничениями; локальная одноразовая среда со сбросом; рабочая система с ограниченными действиями.

Рекомендация: выделенный тестовый стенд, явные адреса, тестовые аккаунты, разрешённые данные и пределы нагрузки.

Ответ пользователя: сначала локальная проверка через Docker или проверка на dev-среде. Разрешённые изменения, нагрузка и сброс данных пока не определены.

## Согласовано — раунд 2

- Q4. Подготовка знаний: готовый пакет пользователя или отдельная фаза, в которой агент собирает черновую модель из описания и документов, отмечает пробелы и согласовывает эталон? Рекомендация: отдельные режимы подготовки и запуска.
- Q5. Глубина проверки: UI; API; UI + API + чтение кода и доступных наблюдений БД/событий? Рекомендация: третий вариант с явным указанием недоступных каналов; код приложения не изменяется в ходе QA-запуска.
- Q6. Полномочия: создание тестовых аккаунтов/данных, сброс состояния, ограниченная нагрузка, инъекции сбоев. Рекомендация: локально разрешать работу с выделенным одноразовым окружением, на dev — только с выделенными данными; сбои и интенсивная нагрузка включаются явно.
- Q7. Оркестрация и время: один агент или координатор с независимыми заданиями; 30 минут — общий бюджет или время активных экспериментов? Рекомендация: координатор и до трёх исполнителей при наличии поддержки, общий бюджет включает подготовку и отчёт; отсутствие инструментов явно отмечается.
- Q8. Первые хосты: Codex, Claude Code или оба? Рекомендация: первая рабочая версия для Codex; переносимая основа без обещания совместимости до проверки второго хоста.

Ответы пользователя:

- Q4: агент готовит пакет знаний; пользователь согласовывает правила.
- Q5: UI + API + чтение кода; БД и события — при наличии доступа.
- Q6: полный доступ к локальному стенду, ограниченный доступ на dev; полномочия должны настраиваться. Полный доступ относится к выделенному стенду, а не к произвольным ресурсам машины.
- Q7: структура команды и время работы настраиваются; по умолчанию координатор + исполнители, общий бюджет 20 минут. Пример с 30 минутами не является текущим значением по умолчанию.
- Q8: первая версия для Codex.

## Согласовано — раунд 3

- Q9: первый объект приёмки — демонстрационный Docker-стенд с известными дефектами и корректными сценариями либо реальный проект пользователя? Рекомендация: сначала воспроизводимый демонстрационный стенд, затем реальный проект. Для первого варианта конкретные сценарии и критерии приёмки будут предложены в итоговой спецификации.
- Q10: если во время запуска обнаружен пробел в согласованном эталоне, фиксировать его и продолжать независимые проверки либо запрашивать решение и приостанавливать зависимые сценарии? Рекомендация: в автоматическом запуске фиксировать пробел и продолжать; предположения не превращать в эталон. Уточнения — в режиме подготовки знаний или после отчёта.
- Q11: результат первого выпуска — Markdown + JSON + доказательства и воспроизводимые сценарии либо дополнительно автоматически сгенерированные регрессионные тесты? Рекомендация: Markdown + JSON, покрытие/ограничения, доказательства и replay-сценарии; генерация тестов — отдельный необязательный режим.

Ответы пользователя:

- Q9: сразу реальный проект пользователя; отдельное демонстрационное приложение не входит в первый выпуск.
- Q10: фиксировать пробелы и продолжать независимые проверки; предположение не становится эталоном.
- Q11: первоначально выбран отчёт с доказательствами и replay. Затем пользователь явно изменил ответ на вариант 2: дополнительно обязательна автоматическая генерация регрессионных тестов для последующего запуска в CI.
