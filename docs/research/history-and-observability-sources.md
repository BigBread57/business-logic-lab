# Конкурентная история, наблюдаемость и частичные сбои

Проверено 26 октября 2026 года по первоисточникам. Это исследование и предложения для интервью; программы не устанавливались, приложения не запускались. Дополняет [обзор oracle/model/evaluation](deeper-testing-sources.md) и [аудит текущих возможностей](current-capability-blindspots.md).

## Porcupine: история относительно независимой модели

[Porcupine](https://github.com/anishathalye/porcupine) принимает исполняемую последовательную модель и историю вызовов/ответов, проверяет linearizability и может визуализировать историю. Это существенно сильнее проверки структуры NDJSON, но применимо только после выбора семантики и подготовки модели. Требуются корректные операции, результаты и сведения о порядке; пространству состояний может быть трудно найти решение. Проверены README и описание моделей, инструмент в Business Logic Lab не подключён.

[Jepsen объясняет linearizability](https://jepsen.io/consistency/models/linearizable): результат параллельного исполнения должен допускать корректное последовательное объяснение с учётом порядка непересекающихся операций. Это свойство одной логической сущности; ограничения нескольких объектов и транзакций требуют другого масштаба модели. Не следует требовать его от любого фонового workflow или eventual read model.

**Наш вывод:** для перемещения папок недостаточно проверить два кода ответа. Модель может описывать родителя, версию и допустимые изменения поддерева. Разбиение истории только по ID папки способно потерять инвариант уникальности имён между соседями: область модели определяется правилом, а не удобством группировки. Это проектный вывод, а не обещание готового folder-adapter Porcupine.

## Elle: транзакционные аномалии и границы применимости

[Elle](https://github.com/jepsen-io/elle) проверяет определённые классы аномалий по клиентской истории транзакций и отношениям чтений/записей. README описывает ограниченную полноту и необходимость ручной проверки сообщений об аномалиях; актуальный README отдельно предупреждает об ограничениях некоторых выводов RW workload. Это исследованный пример подхода, не выбранный универсальный checker для наших API и не интегрированная зависимость.

**Наш вывод:** произвольный HTTP-журнал нельзя просто назвать транзакционной историей. Нужны адаптер, доступные наблюдения и явно выбранные свойства. Наличие красивой диаграммы не доказывает бизнес-корректность.

## Toxiproxy: контролируемые условия сети

[Toxiproxy](https://github.com/Shopify/toxiproxy) — TCP proxy для моделирования сетевых условий. Документация описывает в том числе направленные задержки и ошибки соединений. Проект полезен для экспериментов с недоступной зависимостью, потерянным ответом и последующим восстановлением.

**Наш вывод:** это возможный механизм разрешённых fault-сценариев, а не способ автоматически остановить приложение ровно между двумя SQL-операциями. Сбой до обработки, неизвестный результат после отправки и подтверждённое отклонение — разные исходы. После потери ответа надо сверять логическую операцию/объект и её побочные эффекты, а не слепо повторять мутацию. Нужны ограничения стенда и наблюдаемость; установка и воздействие не выполнялись.

## OpenTelemetry: причинные связи между слоями

[Context propagation](https://opentelemetry.io/docs/concepts/context-propagation/) описывает передачу контекста между операциями и сервисами. [Traces/spans](https://opentelemetry.io/docs/concepts/signals/traces/) связывают единицы работы, их контекст, время, события и ссылки. Проверены разделы документации про propagation и spans; интеграция с нашей лабораторией не устанавливалась.

**Наш вывод:** перспективная цель — отдельные run/scenario/action/attempt/session IDs и связь UI → HTTP → задача/событие → чтение результата. Время и имя аккаунта не заменяют причинный идентификатор. Сам span со статусом OK не доказывает commit или бизнес-успех; отсутствие span при sampling также не доказывает, что действие не выполнялось. Точность наблюдений и редактирование секретов нужны независимо от выбранного telemetry-стека.

## Pact: контракт не заменяет функциональную проверку

[Официальное объяснение Pact](https://docs.pact.io/consumer/contract_tests_not_functional_tests) разделяет согласованность сообщений потребителя/поставщика и функциональные проверки побочных эффектов. Контрактный ответ на создание объекта не доказывает корректное сохранение объекта.

**Наш вывод:** OpenAPI/Pact/JSON schema полезны для входов и транспорта, но после загрузки, публикации или переноса надо проверять бизнес-эффект, видимость и связанные состояния. Совпадение UI/API с общей backend-логикой также не является независимым эталоном.

## Что требуется решить до реализации

- Какие процессы требуют независимой модели и какие свойства действительно обещает проект.
- Как перечислять фактические пропуски по функциям/ролям/переходам; по решению Q5 общий вывод о достаточности не присваивается.
- Как сверять неизвестный исход и доказывать независимость остальных действий.
- Как оценивать поиск на реальных исторических дефектах, не раскрывая ответ исполнителю.
- Как изолировать baseline/fixtures и фиксировать полноту наблюдений.

Первые решения пользователя уже записаны в [черновике интервью](../design/testing-improvements-interview.md). Мутационные инструменты изучены как литература, но пользователь выбрал оценку **только на исторически подтверждённых дефектах**, без искусственно внесённых ошибок.
