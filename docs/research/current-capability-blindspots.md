Исторический срез от 26 октября. Для изменений от 2 ноября — [поставка и границы runtime](../verification-runtime.md); этот аудит не описывает новое состояние целиком.

Проверено чтением текущих файлов 26 октября 2026. Без запуска приложений, изменения исходников или новых тестов. Это границы текущей реализации, а не утверждение, что прежние найденные расхождения недействительны.

## 1. Каталог есть, обязательное покрытие остаётся обещанием агента

**Класс: инструкции; автоматического gate нет.** `references/patterns.md:7–9` требует матрицу по функциям, но `assets/pattern-matrix.example.md:38` прямо говорит, что helper её не парсит. `qa.mjs:392–407` строит coverage только по утверждённым rules и наличию хотя бы одного assertion; не знает список выбранных функций, их операций, роли×владельцы×состояния, обязательные паттерны и число вариантов. Один status assertion на правило может сделать его «observed», не показывая глубину исследования. Не измеряется также покрытие достижимых переходов/пар операций.

**Следствие:** длинный отчёт/249 действий не доказывает, что агент не забыл критичный endpoint или ракурс.

**Решение владельца:** что является минимальным достаточным охватом функции и какие пропуски должны запрещать завершение, а какие допустимо откладывать по бюджету?

## 2. Истинность эталона и исследования без oracle — отдельные нерешённые механизмы

**Класс: частично реализовано.** `qa.mjs:76–109` проверяет hash согласованного knowledge и неизменность snapshot; это полезная защита от устаревшего файла. Но approved — содержимое файла, reviewer — непустая строка: функция не подтверждает независимость/правильность требований. Source revision/path хранятся, текущие исходники не перечитываются при runInfo. Правило о пересмотре изменившихся источников остаётся в `references/knowledge.md:11`.

Чистый oracle-free запуск не является отдельным встроенным режимом qa: `initRun:93`, `validateScenario:157–159` и `journal:368` требуют approved rule. `references/exploration.md:13` предлагает обходной путь: native tools + история + агентный отчёт. История без oracle поддерживается, но нет единого first-class manifest/report с типом observation-only, который не требует фиктивной бизнес-привязки.

**Следствие:** код может случайно стать собственным эталоном; наблюдения могут быть привязаны к неотносящемуся правилу для помещения в стандартный отчёт. Это не требуется делать, но API продукта подталкивает к двум разным путям исполнения.

**Решение:** кто/что служит независимым reference oracle, как версионировать соответствие требованиям и коду; нужен ли явно отдельный observation-only run? Уже согласованные два смысловых режима не следует переутверждать, нужно решить их механическую форму.

## 3. Файлы и многие реальные контракты пока не исполняются универсально

**Класс: отсутствующий адаптер + ограниченный генератор.** `qa.mjs:259–261` сериализует body как JSON и выставляет application/json. Нет FormData/binary/file transport; `validateScenario:171–172` поддерживает только шесть обычных HTTP-методов, QUERY для RSA делал внешний адаптер. `explore.mjs:75–140` принимает ограниченный набор schema keywords; patternPlan:28–55 ограничен ASCII-подмножеством. generateSamples:145–172 не выводит зависимости, владельцев, состояния или файлы из OpenAPI автоматически.

**Следствие:** проверка CSV/PDF/архивов/кодировок/потока обработки и бизнес-валидных сложных объектов требует проектных generators/factories и транспорта. Каталог P11/P12 этого не реализует.

**Решение:** какой реальный тип данных/интеграции первым обязан поддерживаться end-to-end, включая valid control, multipart, результат обработки и владение файлом?

## 4. Самостоятельный адаптивный поиск последовательностей не доказан алгоритмом

**Класс: инструкция + ручной проектный suite.** `patterns.md:40–56` требует новые гипотезы и обновление очереди. `generateSamples:145–172` выдаёт заранее заданное число JSON-значений. `loadScenario` в `qa.mjs:335–351` повторяет готовый scenario; он не изобретает новые переходы. `projects/rsa-folders/backend-qa.mjs:36–42,76–152` задаёт фиксированные группы и порядок, основная вариация имён — ASCII по8букв с namespace. Есть отдельные sequence lengths и негативные входы; это не универсальный state machine explorer.

Нет встроенного shrinking/delta-debugging последовательности/файла/расписания, feedback-guided распределения бюджета, графа новых состояний или поиска по покрытию. Агент может написать такой адаптер, но текущий core его не делает.

**Решение:** приоритет — breadth всех функций или глубокий поиск нескольких рискованных; сколько бюджета резервировать на новые состояния, а не повторы готовых кейсов?

## 5. История сохраняется надёжно, её общая бизнес-корректность проверяется лишь выборочно

**Класс: generic structural checker + domain-specific analyzer.** `explore.mjs:260–281` проверяет intents/results/identity/uncertain и явно пишет Structural history only. `projects/rsa-folders/analyze-run.mjs:39–41,66–69` агрегирует duplicate publications и common-version moves; overlap — интервалы proxy, не контроль SQL-interleaving. Это реальные полезные проверки, но не универсальный linearizability/serializability checker, не проверка всех saga-инвариантов и не полная модель состояния.

В `runs/folders-live-20261022-01/live-summary.md:44` задокументировано: UI→HTTP correlation не всегда уникален, labels session объединяют разные HTTP-клиенты аккаунта. Нельзя надёжно восстановить все причины по timestamp/actor/path при нескольких одинаковых одновременных действиях.

**Решение:** какие свойства истории нужны для процесса: один победитель/last-write-wins, отсутствие потерь, атомарность, eventual convergence; какие события/transaction IDs/readback можно наблюдать без ложного вывода? Все свойства не являются универсально обязательными.

## 6. Проверена работоспособность инструментов, не измерена эффективность тестировщика

**Класс: отсутствующий evaluation harness.** `tests/qa.test.mjs`, `tests/explore.test.mjs`, `tests/proxy.test.mjs` покрывают transport/claims/budget/generator/history и корректность generated regression. Реальные прогоны нашли повторяющиеся дефекты и дали доказательства. Но нет контролируемого слепого набора дефектов, holdout-функций, mutation pipeline, учёта false positives/missed known defects, сравнения стратегий с одинаковым бюджетом и проверки, что модель не получила ответ заранее.

44 green tooling tests не означают «агент умеет находить баги в новых функциях». Повтор одной уже известной проблемы6раз проверяет repeatability, а не recall по разным классам.

**Решение:** как измерять улучшение системы: уникальные истинные находки/пропуски/ложные тревоги/воспроизводимость при фиксированном бюджете? Допустимы ли закрытые от агента известные дефекты или безопасные мутации только в отдельной копии/ветке?

## 7. Воспроизводимость данных и окружения в основном организационная

**Класс: инструкции/проектные adapter scripts.** `validateProfile:46–58` принимает reset/fault/team flags, но нет generic reset/fault executor. data_namespace не используется в core как проверяемое ограничение объекта/запроса. namespace в folder suite — prefix имён (`backend-qa.mjs:38–42`), не snapshot DB/очередей/часов/внешних эффектов. `references/results.md:13` требует fresh namespace; `projects/rsa-folders/README.md:9–16` описывает ручной новый run/мigrations/login.

Seed и сохранённые IDs не восстанавливают исходные данные, время, порядок транзакций или сторонние эффекты. Предыдущий live-run использовал9лабораторных документов из предыдущего индекса (`live-summary.md:46`). Это допустимо как описанная предпосылка, но не clean-room воспроизводимость.

**Решение:** обязательна ли чистая воспроизводимая baseline перед run, кто владеет fixtures/cleanup и как отделять тестовую ошибку от contamination/expired preconditions? Dev namespace isolation требует реального enforcement, если агент получает широкие роли.

## 8. Роли исполнителей и единый бюджет не являются универсальным runtime orchestration

**Класс: metadata/instructions + один специальный proxy.** `qa.mjs:38–40` actor содержит только headers_env; нет проверяемой привязки роли, distinct user/session или worker identity. team.workers (`:54–58`) валидируется, но не запускает агентов. Это делает Codex по skill; несколько аккаунтов в Promise.all не доказывают, что несколько независимых AI-агентов исследовали функционал с разными идеями. UI runner действительно использует отдельные contexts, concurrency/API проверки реальны — это не надо обесценивать.

Для HTTP core есть общий meter, для текущего UI/API проекта `projects/rsa-folders/proxy.mjs:19,34–51,83–96` реализует durable250/4cap. Однако role вычисляется по имени analyst/user, session равен actor; generic browser/Kafka/DB/native/fault actions не автоматически включены в тот же limiter. Стандартный report читает только core meter (`qa.mjs:403`); в live-summary отдельно объясняется actual249 при requests0.

**Решение:** обязательны ли независимые модели-исследователи или достаточно независимых actor sessions под одним coordinator; нужен ли единый protocol исполнитель→budget→history для всех transport adapters? Это важнее, чем просто увеличить число agents в профиле.

1. Критерий эффективности: проверяемый blind benchmark/мутации против числа отчётов и повторов.
2. Обязательное покрытие при ограниченном времени: узко/глубоко или широко/поверхностно; какие gaps блокируют завершение.
3. Воспроизводимая baseline и дозволенная наблюдаемость/инструментализация для сложных гонок.
4. Приоритет следующего end-to-end capability: файлы, stateful adaptive search или executable matrix/history semantics.

Эти вопросы — решения пользователя. Факты о текущих возможностях уже выяснены чтением кода; не следует спрашивать пользователя, «умеет ли helper multipart» или «есть ли matrix gate».
