# Валидация предложенного подхода

Дата проверки: 2026-10-22. Проверялись официальные документации; инструменты не устанавливались и не запускались. Это проверка заявленных возможностей, не сравнительный benchmark.

## Вывод

Разделение на агента, формирующего гипотезы, и исполнителя, проверяющего их, обосновано. Для проверяемого результата также нужны независимые ожидания (инварианты или модель), контролируемое исходное состояние, наблюдаемость и запись доказательств. Это логические обязанности; их не обязательно реализовывать отдельными сервисами.

Рекомендация «ИИ + Hypothesis + собственный конкурентный исполнитель» технически возможна, но преждевременна до выбора интерфейсов и MVP. Hypothesis не является обязательной зависимостью любого автономного тестировщика.

## Инструменты

| Инструмент | Подтверждено и границы |
| --- | --- |
| [Hypothesis stateful](https://hypothesis.readthedocs.io/en/latest/stateful.html) | Генерирует последовательности заданных разработчиком действий и параметров, выполняет заданные проверки. Не выводит бизнес-правила из документации автоматически; требует адаптера к системе и корректного управления состоянием для повторов и минимизации. |
| [fast-check model-based](https://fast-check.dev/docs/advanced/model-based-testing/) | Поддерживает команды, условия применимости, проверки и минимизацию последовательностей. Модель должна быть проще реализации, а не её копией. |
| [fast-check scheduler](https://fast-check.dev/docs/advanced/race-conditions/) | Управляет порядком завершения обёрнутых Promise; обёртывание не меняет жизненный цикл исходного Promise. Не контролирует планирование транзакций удалённого сервера. |
| [Schemathesis](https://schemathesis.io/) | Генерация из OpenAPI/GraphQL, контрактные проверки и пользовательские проверки. Есть stateful testing; одинаковое покрытие возможностей для обоих типов схем не проверено. Бизнес-правила добавляются отдельно; одного OpenAPI недостаточно для доменной корректности. |
| [RESTler](https://github.com/microsoft/restler-fuzzer) | Строит грамматику из OpenAPI, выводит producer-consumer dependencies, генерирует последовательности. Встроенные checkers покрывают определённые классы дефектов; не универсальный критерий правильности бизнеса и не готовый многоролевой агент. |
| [Turbo Intruder](https://github.com/PortSwigger/turbo-intruder) | Скриптуемый исполнитель большого числа HTTP-запросов. [PortSwigger описывает его для поиска гонок](https://portswigger.net/web-security/race-conditions). Синхронизация запросов не гарантирует конкретного внутреннего расписания транзакций; результат проверяется отдельно. |
| [Jepsen](https://github.com/jepsen-io/jepsen#design-overview) | Clojure framework: клиенты, генераторы, конкурентные процессы, сбои, история операций и checkers. Требует адаптации и модели корректности; включение в первоначальный UI/API MVP не обосновано. |

## Поправки к организации работы

1. Документация бывает утверждённой спецификацией, устаревшим описанием или предположением. Нужен статус источника; объявлять всю документацию гипотезой нельзя без выбранного правила разрешения противоречий.
2. Доступ к коду полезен для гипотез и локализации. Ожидаемое поведение нельзя получать только из того же кода, который проверяется.
3. Одновременные HTTP-запросы повышают шанс гонки, но не задают точное чередование транзакций. Для устойчивого воспроизведения могут понадобиться точки синхронизации или управление сбоями.
4. Stateful fuzzing, поиск гонок и нагрузочное тестирование — разные режимы. Для нагрузки нужны отдельные профиль, лимиты, метрики, бизнес-проверки и условия остановки; выбор движка пока открыт.
5. Проверка API, БД и событий требует корреляции и согласованного окна наблюдения. Временно расходящиеся состояния не всегда дефект; случайные снимки разных сервисов могут создать ложное нарушение.
6. В примере с одним местом правило «не больше одной подтверждённой брони» проверяет безопасность, но допускает ноль успешных броней. Нужны отдельные требования к успешному завершению при допустимых условиях и к финансовым результатам.
7. Повторный запуск требует восстановления данных, а повтор гонки — записи доступной информации о конкурентном выполнении. Seed не гарантирует повтор внешнего серверного расписания.
8. «Не обнаружено нарушений» означает только результат выполненных проверок. В отчёте обязательны непроверенные правила, блокировки и ограничения наблюдаемости.

Дополнительные источники: [расширение Schemathesis](https://schemathesis.readthedocs.io/en/stable/guides/extending/), [Hypothesis о нестабильных проверках](https://hypothesis.readthedocs.io/en/latest/tutorial/flaky.html). Детальная проверка шести инструментов выполнена исследовательским подагентом; основные возможности Hypothesis, fast-check и Schemathesis дополнительно сверены координатором.

Предварительная рекомендация: формат сценариев и доказательств, изолированные пользовательские сессии, HTTP/UI-адаптеры, явные проверки и журнал запуска. Генераторы Hypothesis/fast-check подключаются по необходимости, когда подготовлены атомарные действия и воспроизводимое управление состоянием. Это направление для обсуждения, не утверждённый стек.
