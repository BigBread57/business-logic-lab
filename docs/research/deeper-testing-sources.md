# Дополнительные источники: правильность результата и качество проверок

Проверено 26 октября 2026 года. Дополнение к [исследованию эвристик](testing-heuristics-sources.md). Ниже разделены сведения источников и предложения для Business Logic Lab. Инструменты не устанавливались, приложения не запускались; наличие ссылки не означает интеграцию в наш навык.

**Решение после интервью:** пользователь выбрал оценку только на исторически подтверждённых дефектах. Описанные ниже мутационные инструменты — изученная альтернатива, не выбранный режим запуска. Остальные решения и открытые вопросы: [дерево интервью](../design/testing-improvements-interview.md).

## 1. Oracle problem: кто определяет правильность

В статье Barr et al. **The Oracle Problem in Software Testing: A Survey** (2015) генерация входов отделена от определения правильности результата. Рассматриваются независимые реализации, частичные отношения между выполнениями и прошлые версии продукта. Регрессионное сравнение предполагает, что старое поведение подходит как эталон; изменение требований может нарушить это предположение. Проверены введение и разделы 5.1–5.3 полного доступного текста, а не только abstract. [PDF авторского университетского архива](https://discovery.ucl.ac.uk/id/eprint/1471263/1/06963470.pdf), [запись публикации](https://discovery.ucl.ac.uk/id/eprint/1471263/).

**Вывод для проекта:** у каждой проверки нужна опора ожидания: согласованное правило, независимая модель, подтверждённое отношение или только исследовательская гипотеза. UI и API, использующие одну ошибочную backend-логику, могут совпасть и оба быть неверными. Из кода можно выводить идеи, но копирование его вычислений в проверку рискует закрепить ошибку. Если ожидаемый результат неизвестен, сохранять наблюдение и вопрос вместо произвольного pass/fail.

## 2. Metamorphic и differential testing

**A Survey on Metamorphic Testing**, Segura et al. (2016), описывает проверку связей между результатами после преобразования входа. Это помогает без точного ответа для каждого отдельного запуска. Качество отношений и исходных данных влияет на обнаружение ошибок; композиция преобразований требует обоснования. Проверены введение и относящиеся к ограничениям/отношениям разделы доступной accepted version. Исторические оценки инструментов в статье относятся к 2016 году. [Полный текст](https://eprints.whiterose.ac.uk/id/eprint/110335/1/segura16-tse.pdf), [запись публикации](https://eprints.whiterose.ac.uk/id/eprint/110335/).

**Предлагаемые отношения для наших сценариев, требующие проверки семантики:**

- Переименование папки сохраняет её ID, владельца и состав детей, если это предусмотрено правилами.
- Изменение размера страницы сохраняет объединение результатов при фиксированном наборе данных и стабильной сортировке.
- Разрешённые варианты представления одного файла дают эквивалентные бизнес-данные, если форматирование не имеет смысла для обработки.
- Независимые операции дают одинаковый итог в обоих порядках, только если действительно должны коммутировать.

Differential testing сравнивает реализации/версии или независимые способы получить результат. Для API, UI и экспорта полезно сравнивать согласованные свойства, предварительно учитывая разрешённые различия. Само расхождение — сигнал для расследования; совпадение нескольких поверхностей с общим кодом не является независимым доказательством правильности. Основа этого ограничения — обзор oracle problem выше.

## 3. Проверять способность тестов замечать ошибки

**Stryker** вносит контролируемые изменения кода и проверяет реакцию тестов. Официальная документация различает killed, survived, no coverage, timeout и ошибки запуска/компиляции. В стандартной метрике detected включает timeout, поэтому высокий mutation score не равен точному объяснению бизнес-дефекта. Эквивалентные мутации могут не менять наблюдаемое поведение: требование всегда получить 100% некорректно. [Состояния и метрики](https://stryker-mutator.io/docs/mutation-testing-elements/mutant-states-and-metrics/), [эквивалентные мутации](https://stryker-mutator.io/docs/mutation-testing-elements/equivalent-mutants/).

Stryker предлагает варианты для JS/TS, .NET и Scala; **PIT** — для Java/JVM. Это примеры подхода, а не универсальная зависимость для нашего Python/TS стенда. [Stryker](https://stryker-mutator.io/docs/), [PIT](https://pitest.org/).

**Вывод для проекта:** прохождение внутренних тестов лаборатории проверяет её механизмы, но не доказывает способность агента находить неизвестные ошибки. Нужна отдельная оценка: одноразовые копии целевого приложения с заранее известными дефектами и корректными контрольными вариантами. Измерять найденные/пропущенные дефекты, ложные обвинения, точность причины и пригодность воспроизведения. Ошибка инфраструктуры и таймаут должны учитываться отдельно от подтверждённого обнаружения. Изменять реальные исходники приложения для такой оценки без отдельного согласованного режима не предлагается.

## 4. Model-based testing: покрытие заданной модели

**GraphWalker** генерирует пути по направленному графу состояний и переходов. Исполнение этих шагов в приложении требует адаптеров. Проверены официальный репозиторий и документация по моделям/остановке. [Текущий Rust-репозиторий](https://github.com/GraphWalker/graphwalker-rs), [model-based testing](https://graphwalker.github.io/graphwalker-rs/model-based-testing.html).

Устаревший Java-репозиторий архивирован владельцем **17 октября 2026 года**; его нельзя без оговорки представлять как текущий активный проект. [Архивный репозиторий](https://github.com/GraphWalker/graphwalker-project).

Документация различает покрытие вершин, рёбер, требований, ограничение времени и длины. Важный нюанс: `requirement_coverage` при отсутствии требований считается выполненным. Посещение всех рёбер не означает проверку всех последовательностей или конкурентных расписаний. [Условия остановки](https://graphwalker.github.io/graphwalker-rs/stop-conditions.html).

**Вывод для проекта:** добавить к каталогу направлений проверяемую модель критического процесса: состояния, разрешённые и запрещённые переходы, предусловия, постусловия, права и побочные эффекты. Отчёт должен указывать размер/версию модели и фактически проверенные переходы. Неполная или пустая модель не должна превращаться в «всё покрыто». Полное покрытие модели не доказывает полноту самой модели. Наличие у GraphWalker MCP не означает, что он уже настроен или проверен у нас.

## Слепые зоны, которые следует закрыть

Это предложения, не утверждение о реализованных возможностях:

1. **Независимость ожиданий:** не выводить одновременно действие и правильный ответ только из одного production-кода.
2. **Ложная эквивалентность:** перед сравнением UI/API/экспорта, порядков действий и преобразований данных проверять применимость отношения.
3. **Пустое покрытие:** отклонять общую оценку полноты без перечисленных состояний, правил и доказательств исполнения.
4. **Качество проверяющего:** измерять пропуски и ложные находки на известных дефектах, отдельно от числа операций и внутренних unit-тестов.
5. **Последовательности:** проверять запрещённые переходы, повторы и историю, а не только каждую операцию по отдельности. Конкурентные расписания требуют отдельного подхода и не закрываются обходом графа.

## Исходные вопросы исследования и принятые решения

1. Оценка эффективности: выбраны только исторически подтверждённые дефекты и слепые прогоны проблемной/исправленной версий; новые искусственные мутации не выбраны.
2. Независимые модели выбраны для критичных процессов, правила — для остальных. Агент выбирает пример и порядок технической реализации; отдельный выбор пользователя в Q7 признан излишним и снят.
3. При исчерпании бюджета перечислять пропуски без общего вывода о достаточности; это решение Q5 заменяет первоначальную рекомендацию статуса «проверка неполная».
