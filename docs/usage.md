# Использование

Навык находится в `.agents/skills/business-logic-qa/`. Он доступен в Codex при работе из этого проекта. Для другого проекта скопируйте эту папку в его `.agents/skills/` или установите её в каталог пользовательских навыков. Глобальная установка здесь не выполнялась.

Требуется Node 22+. Внешних npm-зависимостей нет. Браузер, доступ к брокеру и целевые тестовые harness предоставляет хост агента / проект.

Для длительной работы начните с [кампании](reference/campaigns.md): она связывает прогоны, сценарии, версии, дефекты и незавершённые проверки. [Самостоятельный пример](../examples/campaign-demo.mjs) работает без инфраструктуры конкретного приложения: `npm run demo -- --out work/my-first-campaign`, с новым выходным каталогом.

| Ситуация | Действие |
| --- | --- |
| Первый запуск | Зафиксировать область, ожидания/вопросы, сохранность; создать кампанию и зарегистрировать прогон |
| Продолжение | `npm run campaign -- resume --campaign DIR`; сначала сверить неизвестные эффекты |
| Обновление версии | Сохранить реальные версии, передать `--versions FILE` в plan/resume и проверить затронутые сценарии |
| Завершение | Зарегистрировать приложения и выполнить report с `--require-reconciled true` |

Дополнительные контракты: [адаптеры](reference/adapters.md), [окружения](reference/environments.md), [результаты native-тестов](reference/test-artifacts.md). Профиль только с native-адаптерами может не содержать HTTP targets и origins.

## Подготовка

Пример задания Codex:

> Используй $business-logic-qa. Изучи выбранные репозитории и контракты процесса создания, изменения и удаления объекта. Создай кампанию, предложи правила и запиши неизвестные ожидания. Начни с одного синтетического объекта и проверь его конечное состояние через независимый канал. Используй разрешённый локальный/dev-стенд; настрой роли, общие лимиты и сохранность по задаче.

После реального согласования отметить выбранные правила approved, создать новую версию knowledge и записать её согласование командой `approve`. Не менять candidate на approved только ради запуска.

Перед запуском агент заполняет [план тестирования](../.agents/skills/business-logic-qa/assets/test-plan.example.md) по [инструкции](../.agents/skills/business-logic-qa/references/planning.md). По исходной задаче определяет функционал, роли, аккаунты, состав команды, конкурентные действия, нагрузку и негативные сценарии; показывает разрешённые настройки до старта бюджета. Уже заданные настройки используются без повторных вопросов. Недостающие обязательные решения уточняются через агента.

Для каждой выбранной функции агент также составляет [матрицу паттернов и проектных гипотез](../.agents/skills/business-logic-qa/assets/pattern-matrix.example.md) по [библиотеке направлений](../.agents/skills/business-logic-qa/references/patterns.md). В отчёте видны неприменимость с причиной, неизвестная применимость, блокировка и пропуск по бюджету. Матрица ведётся агентом; helper не проверяет её Markdown автоматически. [Примеры: файлы, папки и чужие объекты](design/pattern-application-examples.md).

Например: «Проверь одновременное назначение диалога: два исполнителя с ролью оператора, отдельные аккаунты, общий диалог; проверь также повтор запроса, чужой диалог и пропуск шага. Нагрузка — 40 повторов с параллелизмом 2, максимум 200 запросов, бюджет 20 минут». Это пример задания, а конкретные роли/лимиты агент выбирает по вашей задаче и среде. Если права или правильный результат неизвестны, они остаются открытыми вопросами.

Сохранить заполненный `test-plan.md` рядом с run и заданиями исполнителям. Это документ, которым руководствуется агент: helper не читает назначения ролей из Markdown. В profile `actors` остаются ссылками на credentials; роли и распределение исполнителей задаются планом. Общий лимит нагрузки делится между исполнителями, а не выдаётся каждому целиком.

## Команды

Из корня проекта; `Q` — путь к helper. Все входные файлы — JSON.

```sh
Q=.agents/skills/business-logic-qa/scripts/qa.mjs
node "$Q" --help
node "$Q" validate --config profile.json
node "$Q" approve --knowledge knowledge.approved.json --out approval.json --by reviewer
node "$Q" init --config profile.json --knowledge knowledge.approved.json --approval approval.json --out runs/run-01
node "$Q" status --run runs/run-01
node "$Q" execute --run runs/run-01 --scenario scenario.json --id experiment-01
node "$Q" report --run runs/run-01
```

Шаблон профиля сначала заполняется реальными адресами и полномочиями. `validate` проверяет структуру, а не доступность/правильность выбранного стенда. Вывод `execute` краткий, доказательства хранятся в `results/`. Exit 2 означает наблюдавшееся нарушение, 3 — заблокированную/неопределённую проверку, 1 — ошибку входа/инструмента. Не считать nonzero поводом автоматически повторить мутацию.

Команды нагрузки и регрессий:

```sh
node "$Q" load --run runs/run-01 --scenario scenario.json --iterations 5 --concurrency 2
node "$Q" confirm --run runs/run-01 --id experiment-01 --rationale 'Concrete observed evidence contradicts approved rule'
node "$Q" regression --run runs/run-01 --id experiment-01 --out runs/run-01/regressions/defect.test.mjs
node "$Q" verify-regression --run runs/run-01 --id experiment-01
node "$Q" report --run runs/run-01
```

`confirm` — вывод координатора по доказательствам, не автоматическое доказательство скрипта. Для запуска теста отдельно / в CI: `node --test <defect.test.mjs>`, рядом должна лежать созданная `.fixtures`-папка. В CI нужны те же разрешённые адреса и секреты через env. Подключение теста к реальному pipeline выполняется отдельно.

## Структура запуска

- `run.json`: снимки профиля и правил, согласование и исходный deadline.
- `meter.json`: глобальный счётчик запросов и активные запросы.
- `claims/`: выданные ID операций; claim без результата требует сверки перед повтором.
- `results/`: атомарные записи каждого эксперимента.
- `report.md`, `report.json`: покрытие по выполненным assertions, находки, пробелы, незавершённые операции и latency.
- `regressions/`: тесты и логи их проверки; сгенерированные native-тесты для Kafka/UI также сохраняются здесь.

При продолжении использовать тот же run и его исходный deadline. Если бюджет истёк, явно создать новый запуск; неизвестно завершившиеся операции сначала сверить по корреляции. Helpers сохраняют файлы, но не являются планировщиком моделей: небольшие задания, подагентов и смену контекста организует Codex по навыку.

## Межсервисная проверка

HTTP-сценарий наблюдения downstream не покрывает Kafka-ввод. Для него нужны реальные схемы/проектный harness. Для frontend нужна доступная UI-среда. Неизвестный SLA, отсутствующая роль или канал наблюдения остаются явным ограничением покрытия.

Инструмент не является системной песочницей для произвольных shell/MCP/browser действий. Нагрузочный helper даёт ограниченный повтор сценариев, не заменяет полноценную распределённую нагрузочную платформу. Для сложных профилей использовать проектный k6/Locust и сохранять их результаты с бизнес-проверками.

## Генерация данных и анализ действий

См. [генерацию и исследовательский режим](../.agents/skills/business-logic-qa/references/exploration.md). Агент подготавливает подходящие данные по контрактам и бизнес-условиям, повторяет выбранные функции с разными вводными/последовательностями и сохраняет конкретные значения для replay. Встроенный `explore.mjs` поддерживает ограниченный набор структурных ограничений; состояния, владельцев и зависимости подготавливает агент через реальные проектные инструменты.

`node .agents/skills/business-logic-qa/scripts/explore.mjs --help` показывает команды генерации и структурного анализа истории. Экспортируемые appendIntent/appendResult/appendObservation ведут журнал с ролями, аккаунтами и корреляцией; незавершённые действия остаются неопределёнными. После объединения журналов координатор оценивает общую историю по бизнес-инвариантам. Скрипт анализирует структуру журнала, а не заменяет этот бизнес-анализ. Неизвестные ожидания в исследовательском режиме остаются наблюдениями для владельца процесса.

## Исполняемый исследовательский режим

[Контракты runtime](../.agents/skills/business-logic-qa/references/runtime.md): наблюдения без эталона, общий бюджет адаптеров, multipart/binary, составные данные, поиск и сокращение последовательностей, рецепты подготовки/очистки.

```sh
node .agents/skills/business-logic-qa/scripts/qa.mjs init --mode observation --config profile.json --out runs/new-observations
node .agents/skills/business-logic-qa/scripts/qa.mjs execute --run runs/new-observations --scenario observation.json
node .agents/skills/business-logic-qa/scripts/qa.mjs report --run runs/new-observations
```

В observation.json указать `mode: "observation"`, вопрос `question` и HTTP steps без rules/assert. Успешное наблюдение имеет исход `observed`, сохраняется в общем отчёте и не доказывает правильность бизнес-поведения. Для проверки согласованных инвариантов использовать отдельный conformance-сценарий.
