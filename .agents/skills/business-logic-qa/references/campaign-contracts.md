# Кампании, прогоны и сверка результатов

Кампания объединяет длительную проверку продукта. Сценарий имеет постоянный ID, выполнение — отдельный ID, прогон — неизменный бюджет и снимок настроек. Один сценарий может выполняться в нескольких прогонах и на разных версиях. Это работает для UI, HTTP, заданий, событий и хранилищ; конкретный транспорт не определяет структуру кампании.

Для первого знакомства запустите [сквозной пример](../../../../examples/campaign-demo.mjs). Он поднимает небольшой HTTP-сервис в своём процессе, выполняет создание/чтение объекта, обращается через native-адаптер, запускает настоящие Node-тесты, проверяет сохраняемое окружение и выпускает отчёт:

```sh
node examples/campaign-demo.mjs --out work/my-first-campaign
```

Выходной каталог должен быть новым. После завершения HTTP-процесс закрывается, файлы и маркер окружения сохраняются. В отчёте есть успешно проверенные сценарии, один пропущенный native-тест с причиной и незапущенный сценарий удаления. Отметка `reconciled: true` означает, что источники учтены, а не что удаление проверено или продукт полностью корректен.

## Постоянные данные

```text
campaign/
  campaign.json       идентичность и каталоги поиска прогонов
  events/             последовательная история изменений с хешами
  report.json         актуальная машинная сводка
  report.md           актуальная читаемая сводка
  reports/UUID/       сохранённые версии сводок
  context.json        компактный контекст продолжения
  context.md
  plan.json           очередь и удержанные сценарии
```

Источники прогонов и приложений читаются без изменения. Каталог кампании можно размещать рядом с каталогами прогонов. Регистрация сохраняет относительные ссылки; при переносе нужно сохранить их структуру. Генерируемые отчёты содержат версии, историю дефектов, оставшуюся работу, незавершённые задания, результаты native-тестов, ограничения и хеши прочитанных источников.

События публикуются после полной записи; каталог `campaign.lock` сериализует изменения между процессами. Контрольная цепочка обнаруживает случайное изменение/пропуск событий, но не является подписью доверенного автора. После аварии исследуйте процесс и внешние эффекты перед ручным устранением оставшегося lock. Сводка при активном writer остаётся несверенной.

## CLI и SDK

```sh
node .agents/skills/business-logic-qa/scripts/campaign.mjs --help
node .agents/skills/business-logic-qa/scripts/campaign.mjs init --campaign work/audit/campaign --record campaign-config.json
node .agents/skills/business-logic-qa/scripts/campaign.mjs scenario-add --campaign work/audit/campaign --record scenario-record.json
node .agents/skills/business-logic-qa/scripts/campaign.mjs run-add --campaign work/audit/campaign --record run-record.json
node .agents/skills/business-logic-qa/scripts/campaign.mjs execution-begin --campaign work/audit/campaign --record execution-record.json
node .agents/skills/business-logic-qa/scripts/campaign.mjs execution-finish --campaign work/audit/campaign --id create-e1 --record completion.json
node .agents/skills/business-logic-qa/scripts/campaign.mjs resume --campaign work/audit/campaign
node .agents/skills/business-logic-qa/scripts/campaign.mjs report --campaign work/audit/campaign --require-reconciled true
```

Файлы JSON в командах — подготовленные входные записи, описанные ниже. SDK экспортирует одноимённые операции `initCampaign`, `addScenario`, `registerRun`, `beginExecution`, `finishExecution`, `reportCampaign`, `resumeCampaign` и дополнительные операции из справки CLI. Рабочий пример их совместного использования — источник примера выше.

### Кампания и прогон

```json
{"id":"product-audit","title":"Проверка управления объектами","run_roots":["work/audit/runs"]}
```

`run_roots` — явно выбранные каталоги поиска, разрешаемые относительно текущего рабочего каталога при создании кампании. При отчёте поиск показывает найденные, но незарегистрированные `run.json`. Без этих каталогов проверяются только явно зарегистрированные прогоны. Поиск ограничен 10000 каталогами, пропускает `.git` и `node_modules`; символические ссылки и ошибки поиска остаются видимыми пробелами.

```json
{"id":"run-01","path":"work/audit/runs/first","versions":{"backend":"actual-commit","schema":"actual-version","runtime":"actual-version"}}
```

Указывайте реальные версии: commit и признак локальных изменений, digest образа, версию схемы и существенные зависимости. Значения выше — обозначения для замены. `sources` принимает массив `{id,path,files}` и сохраняет Git commit/dirty и SHA-256 выбранных lock/config-файлов; отсутствие Git записывается явно. Снимок можно зарегистрировать как приложение `sources`. Инструмент не определяет версии развёрнутых сервисов по одному checkout: их нужно сверять проектными probes.

### Сценарий

```json
{
  "id":"objects.create-read",
  "title":"Создать объект и прочитать из другой сессии",
  "components":["backend"],
  "sources":["contract:objects#create"],
  "patterns":["cross-session","persistence"],
  "remaining":["Создать объект","Прочитать из другой сессии"],
  "oracle":{"kind":"unknown","question":"Какие поля должны сохраняться?"}
}
```

`oracle.kind`: `unknown`, `approved_rule`, `technical_invariant` или `contract`. Известное ожидание содержит `statement` и `source`; для связи с проверяемым правилом используйте также `rule_id`. Неизвестное ожидание содержит `question` и остаётся наблюдением. `sources` и `patterns` дают происхождение гипотезы; не подменяют проверку. Необязательные `depends_on` ссылаются на ранее зарегистрированные сценарии.

Статусы различают подготовку, отсутствие запуска, выполнение, неопределённость, частичное выполнение, успех, наблюдение, нарушение, блокировку, ожидание проверки исправления и исключение. Изменение статуса вручную ограничено подготовкой, блокировкой, повторным открытием и исключением. Исключение требует причины и ссылки на пользовательское решение.

### Выполнение

```json
{"id":"create-e1","scenario_id":"objects.create-read","run_id":"run-01","novelty":"Первое чтение созданного объекта из независимой сессии"}
```

Сначала `execution-begin`, затем фактические действия через runtime, затем `execution-finish`:

```json
{"results":["native-observation-01"],"status":"partial","remaining":["Проверить чтение из другой сессии"],"summary":"Создание наблюдалось, независимое чтение ещё не выполнено"}
```

`results` — ID сохранённых результатов соответствующего прогона. Они могут поступить от HTTP executor или `journal`. Вердикт выводится из этих результатов. `passed` требует conformance-проверок, наблюдение не становится успехом; blocked/inconclusive нельзя переименовать в наблюдение.

Список `remaining` по умолчанию сохраняется. Пустой список передавайте только после явного учёта всех обязательств сценария. Наблюдение/успех при оставшейся работе становятся частичным выполнением. Выполнение без результата завершается только как blocked/uncertain с объяснением. История исходной попытки сохраняется.

## Дефекты и вопросы

`defect-add` принимает `id,title,severity,confidence,basis,executions,rationale`. Severity: critical/high/medium/low; confidence: candidate/confirmed. Для candidate нужны завершённые выполнения с доказательствами и известное основание ожидания.

Confirmed дополнительно требует сохранённого `violation`, подтверждённого через `qa.mjs confirm`, с падающей проверкой точного `basis.rule_id`. Текст правила и ID источника должны совпадать с approved knowledge соответствующего прогона. Поэтому сначала подтвердите finding, а затем завершите выполнение и зарегистрируйте дефект. При неизвестном бизнес-правиле используйте `question`, а не confirmed.

`defect-update` сохраняет историю состояний open/needs_verification/resolved/not_reproduced с объяснением. Для последних двух нужны более позднее независимое успешное выполнение, проверка того же правила, версии и неизменённые доказательства. `not_reproduced` не равнозначен исправлению. Для отдельного regression-сценария задайте `regression_for` с ID дефекта.

Успешный result должен быть новым после регистрации дефекта: повторная ссылка на старый успех не закрывает finding. Сравниваются также текст approved rule и ID источника, поэтому переиспользование одного rule_id с другим смыслом не является проверкой исправления. Для candidate без rule_id разрешено передать `basis` в defect-update и связать наблюдение с согласованным правилом; это сохраняется в истории с rationale. Основание confirmed-дефекта остаётся фиксированным.

`question` сохраняет `id,question,scenarios`; ответ дополнительно содержит `answer,source`. Ответ не заменяет обновление и согласование knowledge перед conformance-запуском.

## План и продолжение

`plan` и `resume` используют состояние кампании. Новые, частичные и явно открытые сценарии попадают в очередь с причиной. Выполненные сценарии возвращаются при изменении версии затронутого компонента или явном запросе проверки исправления. Передайте `--versions versions.json` с целевыми версиями. Это анализ объявленных связей `components`, а не автоматическое доказательство отсутствия влияния других изменений.

Сценарии с неопределёнными действиями, активными заданиями, блокировкой, исключением или неразобранным нарушением остаются в `held`. Начинать такую мутацию повторно следует после reconciliation. Бюджет исходного прогона сохраняется; расширение бюджета оформляйте новым зарегистрированным прогоном.

В `context.md` находятся очередь, удержанные работы, вопросы, версии, дефекты и назначения. Агент сначала читает этот файл, затем открывает только нужные источники.

## Агенты и приложения

`worker` принимает `id,scenarios,namespace,deadline,result_path,charter`. Пространства независимых данных должны различаться. Для конкуренции явно задавайте общий объект и способ наблюдать перекрытие действий. У агента должны быть применимые правила, границы полномочий, общий run, срок и путь результата; полная история переписки обычно не нужна.

`worker-finish` принимает ID задания и `executions,summary`; проверяет завершённые назначенные выполнения и наличие результата по `result_path`. Незавершённые назначения видны в отчёте и удерживают сценарии от повторной выдачи. Координатор проверяет полноту оставшейся работы и собирает общий итог.

`artifact-add` принимает `id,path,kind,summary` и необязательные `scenarios`. Kind: native-tests/chain/report/regression/environment/sources/other. Файлы и деревья каталогов фиксируются с хешами; symlinks отклоняются. Регистрируйте финализированные приложения, а не изменяющийся каталог всей кампании. Для изменившегося приложения используйте новую версию с новым ID.

Native-тесты сначала [импортируются](test-artifacts.md), затем регистрируется их выходной каталог как `native-tests`. Отчёт показывает точные случаи, skips, команду, версии и отсутствующее collection/coverage evidence. Результаты разных наборов не суммируются как уникальное покрытие.

## Финальная сверка

Отчёт выявляет незарегистрированные прогоны в выбранных корнях, результаты без выполнения, пропавшие/изменённые доказательства, незавершённые executions/workers/claims/actions, неучтённые файлы evidence/regressions и повреждённые приложения. Исходные файлы не исправляются автоматически. При ошибках сохраняется частичная сводка; `--require-reconciled true` возвращает nonzero.

Подтверждения и генерацию регрессии выполняйте до финализации execution: они изменяют result JSON. Если источник изменился после фиксации, отчёт покажет `changed_result`. Сохраните историю, изучите изменение и зарегистрируйте новое evidence-backed выполнение; не переписывайте прежний хеш.

Прерванный experiment claim можно сверить после deadline командой `qa.mjs claim-reconcile`: запись содержит `result_id` нового сохранённого наблюдения, `summary` и `attachments`. Claim сохраняется. Для transport action применяется отдельный `action-reconcile`.

Полнота сверки ограничена выбранными корнями и зарегистрированными источниками. Она не восстанавливает отсутствующие исторические файлы и не доказывает полное покрытие приложения.
