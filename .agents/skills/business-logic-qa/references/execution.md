# Execution and ownership

1. Resolve [the task-driven test plan](planning.md) before starting the run; include role/account/worker assignments, negative cases and load responsibilities. Validate the profile. Set exact HTTP origins, named actors, allowed actions, request and parallelism bounds, environment and deadline. Dev requires an explicit finite load limit. Missing endpoint or credentials blocks the corresponding scenario.
2. Start a run. Configuration, knowledge and approval are snapshotted; original `deadline` persists. Check status before issuing a worker batch. Reserve at least the final 10% for reporting and regressions. Cancellation prevents new requests but cannot roll back an accepted server mutation.
3. Build a coverage queue: one entry per rule and relevant perspective. Use full flows, invalid transitions, same/different rights, ownership, retries, stale state, parallel actions and bounded load. Include valid controls; rejected inputs alone do not prove correct allowed behavior.
4. Dispatch the saved worker charters with their application roles/accounts and scenario subsets. Use separate data namespaces for independent tasks and explicitly shared objects/barriers for concurrency tasks. Each worker writes its own experiment result; the coordinator alone assembles reports. Browser workers require separate contexts/storage states, not just tabs. Avoid sharing an unauthenticated browser singleton across workers.
5. Create `scenario.json` from the asset. Each HTTP request names its configured target and actor. Use captures to correlate actual generated IDs. `${var}` inserts scenario variables; `${env:NAME}` resolves explicitly referenced environment variables. The executor also supplies `${run_id}` and `${correlation_id}`.
6. Check business expectations against approved rule IDs. For eventual reads set `poll_ms` and a rule-derived `within_ms`; keep them within the run budget. A timeout/network problem is blocked, while an observed mismatching final assertion is a violation. A non-JSON response to a JSON assertion is inconclusive.
7. Use `load` only with the configured allowance. It executes a scenario repeatedly with bounded concurrency; each iteration has its own correlation ID. Scripts enforce request, concurrency and deadline caps. Native tools use the [shared action protocol](runtime.md) for each primitive operation; uninstrumented tools remain a coverage/accounting gap.

An experiment ID is claimed once. If interrupted before a result is recorded, status/report shows an uncertain claim. Do not delete it and retry a mutation blindly; reconcile the target using correlation IDs, journal what happened and assign a new experiment only when repetition is appropriate.

For external UI/broker observations, `journal` accepts a record with `id`, `rules`, `outcome`, `summary`, `attachments` (existing files relative to run), and `checks` (`rule`, `expected`, `actual`, `passed`). For pass/violation every named rule needs an explicit check. Include transport, actor, before/action/after evidence and repeatability. Use a new ID; journal cannot take over an HTTP worker's claim. Save reconciliation under a new observation ID, then use `claim-reconcile` to link it while preserving the original claim. It is agent-supplied evidence, not independently verified by the helper; the report labels its origin.

Use `expiry_outcome: "inconclusive"` when the polling window is an exploration limit rather than an approved SLA. The normal assertion-failure outcome is a violation; a network timeout remains blocked. For security-sensitive checks expect status and response shape before checking domain fields so that a login error is not misreported as corrupt business data.

Observation-only scenarios, multipart/binary uploads, state search and owned environment lifecycle use the contracts in [runtime.md](runtime.md). Prepare a fresh environment before starting the QA clock.
